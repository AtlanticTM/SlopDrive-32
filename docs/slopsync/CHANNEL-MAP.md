# SlopSync Channel Map — the one-pager

How channels work, in three sentences: every data/control frame carries a
16-bit **channel id**; the hub's **catalog** describes what each id is (its
class, layout, rates, access) so a generic client needs no prior knowledge;
ids `0x0000–0x007F` belong to the **protocol** (same on every hub, registered
in the SlopSync registry (`spec/registry/registry.yaml`, sibling repo)), and `0x0080–0x7FFF` belong to
the **device** (each hub allocates its own, self-described by its catalog).
This file is the human-readable map; `registry.yaml` and the device catalog
remain the wire truth. The two tables below are GENERATED by
[`tools/gen_channel_map.py`](../../tools/gen_channel_map.py) (`--check`
verifies they match; never hand-edit inside a GENERATED marker pair) —
everything else on this page is hand-maintained prose. Full protocol context
lives in the SlopSync repo’s `spec/SPEC.md` §8 (Catalog); the sub-slot convention below was
stamped by [RFC-047](RFC-QUEUE.md#rfc-047--the-0xcdss-channel-allocation-grid-structure-over-arrival-order-history) and
[RFC-048](RFC-QUEUE.md#rfc-048--the-rendering-constitution-catalog-vocabulary-capability-interfaces-renderer-law).

## The 0xCDSS allocation grid (device space)

Device ids follow **`0xCDSS`** — read a channel id digit by digit:

| Digit | Meaning | Values |
|---|---|---|
| **C** — class | what KIND of channel | 1=STATE 2=STREAM 3=INTENT 4=EVENT 5=STORE (class id + 1) |
| **D** — domain | what SUBSYSTEM | 0=machine 1=motion 2=pattern (device-chosen; declared in catalog groups); 3=auxiliary, 4=playback, 5=automation reserved for future subsystems; 8-F parked for a future multi-axis convention |
| **S** — family | a related GROUP within the domain | device-chosen (e.g. the SlopMotion tuning trio, or the six fray-d modifier lanes); family **F is admin/meta in every band** (clear-fault, scan, save, reboot-style verbs) |
| **S** — member | which one WITHIN the family | **member 0 is always the family's master** (its own STATE/roster channel, or the sole INTENT verb for a single-writer family) |
| | experimental | `0x7000–0x7FFF` — vendor/experimental play space, never shipped |

**The mirror rule (Phase C4, operator-stamped):** a channel and its paired
writer/twin across class bands share domain+family+member exactly —
`0x1120` slopmotion-limits (STATE) and `0x3120` slopmotion-set (INTENT) are
both domain=motion, family=2, member=0. [The channel grid visual](channel-grid.html)
highlights a cell's mirrors on hover.

**Named reserves** hold a slot without shipping it: `0x1011` battery and
`0x1012` thermal ([RFC-048](RFC-QUEUE.md#rfc-048--the-rendering-constitution-catalog-vocabulary-capability-interfaces-renderer-law) capability interfaces —
this device has no hardware behind either yet).

Worked examples: `0x1100` = STATE·motion, family 0 member 0 (the motion
telemetry channel — the family master). `0x2101` = STREAM·motion, family 0
member 1 (segments). `0x3200` = INTENT·pattern, family 0 member 0 (the
pattern-state writer). `0x30F0` = INTENT·machine, family F member 0
(machine-admin, the admin convention applied to the machine domain).

> into class/domain/family/member live, next to this table.

| 0x000A | pending-pairing | STATE | RFC-027(a) knock-and-approve: the bounded pending list (pairing_pending_max) as protocol state: {generation u16, count u8, flags u8} + slots {instance_id u64, kind u8, expires_s u16, name str16}. Carries `seq_of_state` (34) naming the 0x0003 frame it corresponds to, which is what lets a client that missed the edge reconcile against the latch it DID receive. Emitted on TRANSITIONS ONLY: a repeated ESTOP frame re-broadcasts the STATE (that is §11.2's loss recovery) but does NOT re-emit the edge, because an edge that did not happen is a lie. |

Legality note: Phase C4 is a second **device catalog evolution** (etag
bump), not a protocol change — `0x0080–0x7FFF` is device-allocated space per
the registry, and the frozen conformance mini-catalog uses its own ids and
is untouched by either renumber. Phase C2's entry here once called itself
"the last renumber that will ever be legal"; it was wrong, because the flat
grid it introduced had no room to grow a channel's own related-group
structure without colliding with its neighbors. The family-nibble sub-slot
convention Phase C4 adds is what actually makes this the last one: every
family reserves 15 unused member slots and every domain reserves unused
families, so a new member of an existing concept gets a numeric home instead
of forcing a renumber. Renumbering stays legal in principle until the v1.0
tag binds the never-renumber rule for good (the registry's own header says
so); it should not be needed again.

**The Old column retires at the v1.0 tag.** It exists only to bridge a
renumbering era; once ids stop moving, nothing populates it, and it comes
out of this table entirely rather than sitting frozen at "(new)" forever.
Treat any Old value you see after the tag as a historical curiosity, not a
sign that another renumber is coming.
